# 인증 설계

로그인·로그아웃(AUTH-01~03), 계정 초대와 가입(ACC-03, AUTH-04~05), 비밀번호 초기화(ACC-05, AUTH-06~07)의 구현 기준이다. API 명세 §12에서 미정이던 값을 구현하면서 아래와 같이 정했다. 값은 `backend/src/modules/auth/auth-policy.ts` 한 곳에 모여 있어 팀 합의에 따라 바꿀 수 있다.

## 정한 값

| 항목 | 값 | 이유 |
|---|---|---|
| 세션 저장소 | Redis (`hospital:session:*`) | 서버를 다시 켜도 로그인이 유지되고, 초대 정보와 같은 저장소를 쓴다. |
| 세션 쿠키 | 이름 `connect.sid`, `HttpOnly`, `SameSite=Lax`, HTTPS 접속 시 `Secure` | 자바스크립트가 쿠키를 읽지 못하고, 다른 사이트에서 보낸 POST에는 쿠키가 붙지 않는다. |
| 세션 만료(미사용) | 마지막 요청 후 1시간, 요청마다 연장 | 자리를 비운 화면이 오래 열려 있지 않게 하면서 업무 중에는 끊기지 않는다. |
| 세션 만료(최대) | 로그인 후 12시간 | 근무 한 번 분량. 계속 사용해도 하루에 한 번은 다시 로그인한다. |
| CSRF 방어 | `SameSite=Lax` 쿠키 + JSON 본문만 허용 + CORS 허용 출처 제한 | 별도 CSRF 토큰 없이 프론트엔드를 바꾸지 않고 적용할 수 있다. 프론트와 API가 서로 다른 사이트로 배포되면 다시 검토한다. |
| 로그인 실패 제한 | 같은 IP·이메일 10분에 5회, 같은 IP 전체 10분에 30회. 초과 시 `429 RATE_LIMITED` | 비밀번호 추측을 늦춘다. 성공한 로그인은 세지 않는다. 횟수는 서버 메모리에 둔다. |
| 공개 토큰 API 제한 | IP당 1분에 30회 | 링크 검증·수락 API의 무차별 호출을 막는다. |
| 초대 링크 | 72시간, 1회용 | 메일을 바로 확인하지 못하는 경우를 고려했다. |
| 재설정 링크 | 1시간, 1회용 | 기존 계정의 비밀번호를 바꾸는 링크라 짧게 둔다. |
| 비밀번호 규칙 | 8~128자, 영문(A~Z, a~z)과 숫자를 각각 1자 이상 포함. 특수문자는 선택 | 숫자만 또는 영문만으로 된 쉬운 비밀번호를 막는다. 가입·재설정·관리자 생성 스크립트에 같은 규칙을 적용하고, 로그인에는 적용하지 않아 기존 비밀번호로는 계속 로그인할 수 있다. 위반 시 `400 VALIDATION_ERROR`, 메시지 "비밀번호는 영문과 숫자를 모두 포함해 8자 이상으로 입력해 주세요.", `details`의 `reason`은 `LENGTH` 또는 `COMPOSITION`. |
| 비밀번호 저장 | argon2id 해시 | 원문을 저장하지 않으며 DB가 노출돼도 되돌리기 어렵다. |
| 이메일 | 앞뒤 공백 제거 후 소문자로 저장·비교 | 대소문자만 다른 중복 계정을 막는다. |

## 동작 방식

- **세션에는 계정 ID만 둔다.** 역할·상태·소속은 요청마다 DB에서 읽으므로(`common/middlewares/account-provider.ts`) 권한 변경과 비활성화가 다음 요청부터 바로 적용된다. 비활성화되거나 삭제된 계정의 세션은 그 요청에서 지운다.
- **로그인 시 세션 ID를 새로 발급한다.** 로그인 실패 응답은 이메일이 없는 경우와 비밀번호가 틀린 경우를 구분하지 않으며, 없는 이메일에도 같은 해시 계산을 수행한다. `ACCOUNT_INACTIVE`는 비밀번호가 맞을 때만 알린다.
- **로그아웃은 세션이 없어도 `204`다.** 여러 번 호출해도 결과가 같다.
- **토큰은 32바이트 난수이고 Redis에는 SHA-256 해시만 둔다.** 저장 키에 용도(`invitation`, `password-reset`)가 들어가 서로 바꿔 쓸 수 없다. 메일의 링크는 토큰을 `#token=` 뒤에 두어 서버 접속 기록에 남지 않는다.
- **대상당 유효한 링크는 하나다.** 같은 이메일을 다시 초대하거나 같은 계정의 재설정을 다시 요청하면 이전 링크는 무효가 된다.
- **메일 발송에 실패하면** `503 MAIL_SEND_FAILED`를 반환하고 방금 만든 토큰만 지운다. 이전에 보낸 링크는 그대로 유효하다.
- **수락·재설정은 토큰을 먼저 꺼낸 뒤(원자적 삭제) DB를 바꾼다.** 같은 링크로 동시에 요청해도 한 번만 처리된다. DB 작업이 실패하면 남은 시간만큼 토큰을 되돌려 다시 시도할 수 있다.
- **초대 수락 시 진료과 행을 잠그고 활성 여부를 확인한다.** 진료과 비활성화·삭제와 동시에 실행돼도 비활성 과에 의료진이 생기지 않는다. 이메일 중복은 DB의 유일 제약이 최종 보장한다.
- **비밀번호를 재설정하면 그 계정의 기존 세션이 모두 끊긴다.** 계정별 번호(`hospital:session-epoch:*`)를 올리고, 로그인 때 기록한 번호와 다르면 세션을 버린다. 계정 상태는 바꾸지 않는다.

## 진료과 관리에서 정한 것

- 목록(DEP-01)은 페이지 없이 이름순으로 모두 반환한다. 관리자가 아니면 활성 진료과만 보이고 `status=INACTIVE` 요청은 `403`이다.
- 이름은 앞뒤 공백 제거 후 1~50자다. 등록과 이름 변경 모두 중복이면 `409 DEPARTMENT_NAME_DUPLICATE`다.
- 삭제(DEP-05)는 의사·간호사·예약·접수 중 하나라도 참조하면 `409 DEPARTMENT_IN_USE`다. 취소된 예약도 이력으로 본다.
- 상태 변경·삭제·이름 변경은 진료과 행을 잠근 뒤 확인하고 저장한다. 의료진 소속 변경(DEP-08)도 같은 행을 잠그므로 서로 순서대로 처리된다.

## 명세·OpenAPI에 반영이 필요한 차이

구현하면서 명세에 없던 응답을 추가했다. `docs/api-spec.md`와 `backend/openapi.yaml`은 수정하지 않았으므로 팀 확인 후 반영한다.

| API | 추가·확정한 내용 |
|---|---|
| AUTH-01 | 형식 오류 `400 VALIDATION_ERROR`, 실패 제한 `429 RATE_LIMITED`와 `Retry-After` 헤더 |
| AUTH-02 | 세션이 없거나 만료되어도 `204` |
| AUTH-05 | 비밀번호 규칙(영문+숫자, 8~128자) 위반 `400 VALIDATION_ERROR`, 이메일 중복 `409 ACCOUNT_EMAIL_DUPLICATE`, 초대받은 진료과가 비활성·삭제됨 `409 CONFLICT` |
| AUTH-07 | 만료·사용됨 `410 RESET_LINK_INVALID`, 불일치 `422 PASSWORD_MISMATCH`, 비밀번호 규칙(영문+숫자, 8~128자) 위반 `400 VALIDATION_ERROR` |
| ACC-03 | 이메일 중복 `409 ACCOUNT_EMAIL_DUPLICATE`, 없는 진료과 `404`, 비활성 진료과 `409 CONFLICT`, 발송 실패 `503 MAIL_SEND_FAILED` |
| ACC-05 | 없는 계정 `404`, 발송 실패 `503 MAIL_SEND_FAILED` |
| DEP-01 | 관리자가 아닌 역할의 `status=INACTIVE` 요청 `403 FORBIDDEN` |
| DEP-03 | 이름 중복 `409 DEPARTMENT_NAME_DUPLICATE`, 없는 진료과 `404` |

### 프론트엔드에서 맞춰야 할 오류 표시

백엔드는 아래 오류에 화면에 그대로 보여 줘도 되는 한국어 메시지를 담아 보낸다. 현재 프론트엔드의 `normalizeApiError`(`frontend/src/services/api/errors.ts`)가 상태 코드별 고정 문구로 바꿔 버려서 사용자에게 원인이 보이지 않는다. 2026-11-16에 실제 화면에서 확인했다.

| 화면 | 백엔드 응답 | 현재 화면 문구 |
|---|---|---|
| 초대 가입·비밀번호 재설정에서 규칙에 맞지 않는 비밀번호 | `400 VALIDATION_ERROR` "비밀번호는 영문과 숫자를 모두 포함해 8자 이상으로 입력해 주세요." | "서버에 연결할 수 없습니다. 잠시 후 다시 시도해 주세요." |
| 진료과 등록·이름 변경에서 이미 있는 이름 | `409 DEPARTMENT_NAME_DUPLICATE` "이미 등록된 진료과 이름입니다." | "정보가 변경되었습니다. 새로 조회한 후 다시 시도해 주세요." |

`400` 응답과 `DEPARTMENT_NAME_DUPLICATE` 코드는 서버의 `error.message`를 표시하거나 코드별 문구를 추가하면 해결된다. 가입·재설정 화면에서 같은 규칙을 먼저 검사하면 서버 요청 없이도 안내할 수 있다.

## 알려진 한계

- 로그인 실패 횟수는 서버 프로세스 메모리에 있어 서버를 다시 켜면 초기화되고, 서버를 여러 대로 늘리면 서버마다 따로 센다.
- 프록시 뒤에 배포하면 `trust proxy` 설정이 필요하다. 없으면 모든 요청이 같은 IP로 보이고 `Secure` 쿠키가 붙지 않는다.
- 메일은 SMTP 서버가 요청을 받아들였는지만 확인한다. 수신함 도착은 보장하지 않는다.

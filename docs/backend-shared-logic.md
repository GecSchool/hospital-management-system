# 백엔드 공통 구현 가이드

이 문서는 API를 구현할 때 중복을 줄이고 업무 규칙을 일관되게 적용하기 위한 설계 가이드다. 현재 실제 업무 API나 공통 서비스가 구현되었다는 뜻은 아니다. 외부 계약과 권한은 [API 명세](api-spec.md), 요청·응답 스키마는 [OpenAPI](../backend/openapi.yaml)를 기준으로 한다.

## 예약 가능 여부와 저장

- 관련 API: `APT-01` 일반 예약, `APT-06` 의사 재진 예약, `APT-04` 예약 시간 변경, `SCH-05` 예약 가능 시간 조회.
- 의사와 진료과의 활성·소속, 20분 단위 진료 가능 시간, 휴진, 동일 의사·동일 시각의 취소되지 않은 예약을 일관되게 확인한다. 시간 변경의 `excludeAppointmentId`는 변경 권한과 대상 의사·예약을 검증한 뒤 해당 예약만 제외한다.
- 일반 예약과 재진 예약의 요청·권한은 분리한다. 의사 재진의 환자·진료과·의사는 해당 완료 진료와 접수에서 결정하며 클라이언트 입력을 신뢰하지 않는다.
- 조회 결과는 조회 당시 상태다. 저장·변경 시 다시 확인하며, 예약 중복·휴진 신청·시간표 변경과 동시 실행되어도 규칙이 깨지지 않도록 데이터베이스 제약과 트랜잭션·잠금 전략을 함께 설계한다.

## 예약 접수와 현장 접수

- 관련 API: `REC-01` 접수 생성. 이미 단일 API다.
- 예약 접수는 예약에서 환자·의사·진료과를 가져오고, 현장 접수는 요청값을 검증한다. 각 입력 형식은 상호 배타적으로 처리한다.
- 공통 접수 생성 과정에서 동일 환자·의사·업무 날짜의 미완료 접수, 예약 당일과 예약별 중복 등 해당 규칙을 검증한다. 중복 확인과 생성은 동시에 요청해도 안전하게 처리한다.
- `REC-04` 삭제와 간호 기록 생성 간에도 동일한 잠금 경계를 사용하여 기록이 있는 접수가 삭제되지 않도록 한다. 삭제된 접수는 목록·이력에서 제외하며, 실제 저장 방식은 아직 확정하지 않는다.

## 진료·간호 기록 버전

- 관련 API: `VIS-04~07`, `NUR-02~05`.
- 원본 버전 1 생성, `baseVersionNo`와 최신 버전 비교, 다음 버전 번호 할당, 충돌 처리, 기존 버전 보존의 공통 절차를 재사용한다. 번호 할당과 삽입은 트랜잭션과 `(recordId, versionNo)` 유일성으로 보호한다.
- 기록 종류별 저장소·본문 검증과 권한 검사는 구분한다. 진료 기록은 해당 진료 담당 의사, 간호 기록은 최초 작성 간호사만 정정할 수 있다. 원본·정정의 작성자와 시각은 보존한다.

## 의사 미처리 업무 확인

- 관련 API: `ACC-04` 계정 비활성화, `DEP-08` 소속 변경.
- 오늘 이후 미접수 유효 예약 또는 미완료 접수·진료가 있는지를 같은 기준으로 확인한다. 지난 날짜의 미접수 예약은 차단 조건이 아니다.
- 두 작업은 서로 다른 권한과 결과를 유지한다. 확인 후 변경하기까지 업무 상태가 바뀌어 제한이 우회되지 않도록 트랜잭션 경계도 고려한다.

## 화면용 진행 상태 계산

- 관련 API: 예약 목록 `APT-02`, 접수 목록 `REC-02`, 환자 이력, 의사 환자 목록 `VIS-01`, 의사 일정 `DASH-02`, 직원 대시보드 `DASH-01` 등.
- 예약·접수·진료를 조합한 `displayStatus`와 상태 필터의 기준을 공통으로 관리한다. 삭제된 접수는 합성에서 제외하고 보존된 예약을 기준으로 판단한다.
- 목록별 권한과 반환 필드는 별도로 적용한다. 여러 행을 처리할 때 행마다 개별 조회를 반복하지 않도록 관계를 묶어 조회하는 방식을 검토한다.

## 초대·비밀번호 재설정

- 관련 API: `ACC-03`, `AUTH-04~07`, `ACC-05`.
- 이메일 발송, 토큰 생성·조회·만료 확인, 비밀번호 형식 검증은 공통화할 수 있다. 초대와 비밀번호 재설정 토큰은 용도를 구분해 다른 흐름에서 사용할 수 없게 한다.
- 초대 수락에 따른 계정 생성과 기존 계정의 비밀번호 변경은 별도 업무로 구현한다. 메일·Redis·DB 실패 복구와 토큰의 상세 정책은 아직 미정이다.

## 진료과 의료진과 예약용 의사 조회

- 관련 API: `DEP-06`, `DEP-07`.
- 진료과 소속 의료진 검색 부분은 재사용할 수 있다. 관리자용은 의사·간호사와 페이지네이션이 필요하고, 예약용은 의사 요약과 활성 조건이 필요하므로 API별 권한·반환값·범위를 그대로 유지한다.

## 대시보드와 목록 조회

- 관련 API: `DASH-01`, `APT-02`, `REC-02`; 필요 시 의사 일정 `DASH-02`에도 해당 조회 규칙을 재사용한다.
- 직원 대시보드는 단일 API를 유지하되, 예약·접수 미리보기에 목록의 조회 조건과 상태 계산을 재사용한다. 전체 목록과 대시보드의 반환량·정렬 조건은 각각 유지한다.
- 서버가 자기 API를 HTTP로 호출할 필요는 없다. 내부 서비스 또는 저장소 조회를 조합하되, 별개의 DB 조회를 사용한다면 여러 데이터가 항상 동일한 시점이라는 보장은 별도로 설계해야 한다.

## 조회 API 통합 시 유의점

- `APT-02`는 선택적인 `patientId` 정확 일치 조건으로 환자 예약 이력에도 사용한다.
- `REC-02`는 `date` 또는 `patientId` 중 하나 이상을 요구한다. 둘 다 있으면 함께 적용하고 둘 다 없거나 빈 값만 있으면 `400 VALIDATION_ERROR`를 반환한다.
- 환자 ID가 있어도 간호사의 본인 진료과 제한을 서버에서 적용한다. 직원용 환자번호 등 역할별 반환 스키마와 기존 페이지네이션을 유지한다.
- 예약 목록·환자 이력에 필요한 정렬과 취소 예약 표시 기준은 구현 시 화면에 맞춰 확인한다. 날짜를 생략한 환자별 접수 조회에서도 삭제된 접수는 제외한다.

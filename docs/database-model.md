# 데이터베이스 모델 및 마이그레이션

최종 논리 ERD와 [API 명세](api-spec.md)를 기준으로 PostgreSQL 및 Prisma 7 스키마를 작성한다. 이는 데이터 모델과 초기 마이그레이션이며 업무 API, 인증·권한, 암호화, 트랜잭션 서비스가 구현되었다는 뜻은 아니다. 이 저장소는 실제 환자 정보를 취급하지 않으며 개발·시연에는 가상 데이터만 사용한다.

## 식별자와 관계

- 계정은 역할 한 개를 가지며 직원·관리자는 별도 테이블이 없다. 의사·간호사의 PK는 계정 ID이자 계정 FK다. API `doctorId`와 의사 응답 `id`의 값은 해당 의사의 계정 ID다.
- `doctor_availability`의 PK는 `(doctor_account_id, day_of_week, start_minute)`, `doctor_leaves`의 PK는 `(doctor_account_id, date)`다. 휴진은 하루 전체이며 휴진 ID는 없다.
- 진료·간호 기록 버전의 PK는 각각 `(record_id, version_no)`다. 별도 버전 ID는 없다. 본체 ID는 그대로 유지한다.
- 간호 기록 본체는 최초 작성 간호사를 가리키고, 각 버전은 실제 작성 간호사를 별도로 가리킨다. 같은 과의 다른 간호사도 정정할 수 있다. 최초 작성 시 본체 작성자와 버전 1 작성자를 일치시키는 것은 서비스의 책임이다.
- 예약은 등록 계정과 선택적 취소 계정을 갖는다. 접수의 예약 FK는 선택적·유일하므로 현장 접수가 가능하고 예약당 접수는 최대 한 건이다. 접수 삭제는 물리 삭제이며 예약은 유지한다.
- 접수에는 당시 환자·의사·진료과를 저장한다. 진료는 접수에서 의사와 과를 읽는다. 진료의 접수 FK와 진료 기록의 진료 FK는 각각 유일하다.

## 날짜와 시간

- `birth_date`와 휴진 `date`는 PostgreSQL `DATE`다. 예약·접수·진료·버전 작성 일시는 `TIMESTAMPTZ(3)`이며 API에 오프셋을 포함해 전달한다. 업무 날짜·요일은 `Asia/Seoul` 기준이다.
- 주간 진료 가능 시간은 0=일요일~6=토요일과 자정부터의 정수 분을 저장한다. 예: `09:00`=540, `24:00`=1440. 20분 간격과 시간 범위, 동일 의사·요일의 구간 겹침 방지는 마이그레이션 SQL의 CHECK·GiST 배제 제약으로 강제한다. 연결된 구간은 서비스가 병합한다.
- 시간표는 전체 교체하며 이력을 보존하지 않는다. 과거 일정 화면의 가능 시간은 현재 시간표 기준으로 계산되므로 과거 설정의 재현을 보장하지 않는다.

## 주민등록번호

- `resident_number_ciphertext`는 원본 번호를 복호화할 수 있는 인증 암호화 결과를 저장할 자리다. `resident_number_lookup`은 형식이 정규화된 동일 번호에 대해 동일한 **HMAC-SHA-256** 32바이트 값을 저장하며 유일 인덱스가 있다. 일반 해시나 암호문 자체를 중복 판정에 사용하지 않는다.
- 중복 보장은 API 구현이 모든 쓰기에서 같은 정규화와 안정적인 비밀키를 사용해 조회값을 올바르게 생성한다는 전제에 의존한다. DB는 전달된 조회값의 유일성만 보장하며, 서로 다른 조회값이 같은 실제 번호에서 유래했는지 확인할 수 없다.
- 키는 저장소와 DB에 저장하지 않으며 암호화·HMAC 키를 분리한다. 조회키 변경은 기존 값과 신규 값이 공존하는 동안 중복 등록이 생기지 않도록 재계산·전환 계획이 필요하다. AES-256-GCM 암호문의 버전 1 형식은 버전 1바이트, IV 12바이트, 인증 태그 16바이트, 암호문 순이다. 현재 단일 키만 지원하므로 키 교체는 별도 재암호화 절차가 구현되기 전에는 수행하지 않는다.
- 직원은 주민등록번호를 변경할 수 있다. 새 암호문·조회값·생년월일을 단일 DB 갱신으로 함께 저장하고 다른 환자와의 중복을 거부한다. 응답에서는 마스킹하고 요청 본문 외 URL·로그에 번호를 남기지 않는다.

## DB가 강제하는 제약과 서비스 책임

초기 마이그레이션은 복합 PK·FK·유일 제약 외에도 유효 예약 시간의 부분 유일 인덱스, 진료 시간 겹침 방지, 버전 번호·정정 사유, 방문 완료 시각 및 예약 취소 정보의 일관성, 중복 조회값의 크기 제약을 포함한다. `btree_gist` 확장 설치 권한이 필요하다. 수동 SQL 제약은 Prisma 스키마만으로 모두 표현되지 않으므로 마이그레이션 이력을 기준으로 보존하고 스키마 변경 시 함께 검토한다.

다음 규칙은 초기 DB 제약만으로 완결되지 않으며 업무 API 구현 시 권한 검증·잠금·트랜잭션으로 보장해야 한다.

- 계정 역할과 의사·간호사 세부 테이블의 일치 및 마지막 활성 관리자 보호
- 진료 가능 시간·휴진과 예약 등록/변경의 동시성, 향후 예약이 있는 경우 시간표·휴진 변경 제한
- 동일 환자·의사·업무 날짜의 미완료 접수 제한, 호출 교체와 진료 중 중복 호출·진료 방지
- 예약 접수 시 예약과 접수의 환자·의사·진료과 일치, 접수 담당 의사 변경 금지
- 같은 과 간호사의 기록 정정 및 진료 담당 의사 정정 권한, 최초 버전 생성·최신 버전 충돌 검사와 원본·이전 버전 보존
- 환자별 접근 범위, 관리자·직원의 진료·간호 본문 접근 제한, 마스킹과 민감 정보 로그 방지

간호 기록이나 진료가 참조하는 접수는 FK의 `RESTRICT`로 물리 삭제를 방지한다. 삭제 확인과 간호 기록 생성의 경합도 API가 같은 트랜잭션·잠금 경계에서 처리해야 한다.

## 팀 개발 환경

Node 버전은 저장소 `.nvmrc`를 사용한다. `backend/.env.example`을 참고해 로컬 `backend/.env`에 테스트 전용 `DATABASE_URL`을 설정한다. 암호화·조회용 키 예제나 기본값은 제공하지 않는다. 공유 DB에 기존 데이터가 있다면 이 초기 마이그레이션을 바로 적용하지 말고 현재 스키마와 마이그레이션 이력을 확인한다.

```bash
npm install
npm run prisma:validate --workspace backend
npm run prisma:generate --workspace backend
npm run db:deploy --workspace backend
npm run db:status --workspace backend
```

스키마를 바꾸면 개발 DB에서 `npm run db:migrate --workspace backend -- --name 변경명`으로 새 마이그레이션을 만들고 SQL을 검토한다. Prisma 스키마와 `prisma/migrations` 전체를 함께 커밋한다. `db:deploy`는 커밋된 마이그레이션을 적용하며 클라이언트를 생성하지 않으므로 `prisma:generate`를 별도로 실행한다.

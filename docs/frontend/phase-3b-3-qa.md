# Phase 3B-3 직원 통합 QA

## 실행 결과와 범위

feat/frontend에서 기존 미커밋 파일을 보존했다. 기존 170개 테스트를 먼저 실행해 모두 통과했고, 고정된 서울 업무 시각 2026-11-09 12:00(+09:00)의 통합 테스트 2개를 추가했다. 최종 결과는 아래 로드맵의 실행 기록을 따른다. 실제 업무 API/DB 통합이나 브라우저 전체 E2E와 구별한다.

- 기존 UI 테스트: staff/1234, 대시보드, 환자 검색/등록/수정, 역할별 접근 제한, 예약 선택/슬롯/변경/취소, 접수 확인/현장 접수/삭제/제한/오류/중복 제출 통과.
- 추가 통합 시나리오: 신규 환자 → 예약 생성 → 동일 ID 시간 변경 → 당일 예약 접수 → REGISTERED 및 변경/취소 거부 → 삭제 → 원래 예약 BOOKED 복구/슬롯 점유 유지 → 같은 예약 재접수 → 삭제 → 예약 취소/CANCELLED 보존/슬롯 해제 → 현장 접수/새 예약 미생성 → 중복 거부 → 환자 이름 수정/각 조회에 최신 이름 투영.
- 추가 Query hook 테스트: 실제 AppProviders/QueryClient에 예약 상세·접수 목록·환자 접수 이력·대시보드 조회를 동시에 마운트했다. 기존 useBookingWrite 및 refreshPatient를 통해 접수 생성/삭제/환자 수정 시 각 조회가 다시 실행되어 같은 이름·ID·상태를 표시함을 확인했다.
- 기존 서비스/화면 테스트의 간호 기록·진료 시작 후 삭제 제한, 호출 접수 삭제/해제, 슬롯 충돌, 변경 없음·중복 제출·다른 역할 차단도 재실행했다. 임의 호출·진료 업무를 추가하지 않았다.

## 안전한 수동 Chrome 검증 절차

1. 사용자가 직접 독립 Chrome 테스트 창을 연다. 저장소 루트에서 `npm run dev:mock --workspace frontend -- --host 127.0.0.1` 실행 후 출력된 주소를 사용한다. 다른 앱이 포트를 사용하면 출력된 새 포트를 따른다. 새로고침은 Mock 데이터/로그인을 초기화하므로 전체 흐름 중 피한다.
2. staff/1234 → 대시보드 → 환자 관리. 가상 환자 이름, 주민번호 예시 900101-0000000, 연락처 010-0000-1122로 등록 → 상세 → 이름/연락처 수정 → 목록·상세 일치 확인.
3. 같은 환자 상세 → 예약 등록. 진료과/의사/날짜/사용 가능한 시간을 선택하고 확인 후 등록한다. 변경 화면에서 현재 시간이 선택되고 저장은 비활성인지 확인 → 다른 슬롯 선택 → 변경 → 동일 예약 ID/바뀐 시간 확인. 별도 예약을 취소해 CANCELLED 보존 확인.
4. 예약 접수 검증은 **당일 근무 시간에 아직 사용 가능한 슬롯**이 있어야 한다. 미래 예약이면 접수 버튼 제한을 먼저 확인한다. 당일 유효 예약 상세 → 접수 확인 → 접수 현황 → 예약 상세 REGISTERED 및 변경/취소 차단 → 환자 접수 이력·대시보드 갱신 확인.
5. 접수 삭제 → 목록/이력에서 제외, 예약 상세는 BOOKED/원래 ID 유지 확인 → 같은 예약 재접수 → 새 접수 ID 확인. 현장 접수도 별도 환자로 생성해 예약 이력이 증가하지 않고 중복은 차단되는지 확인한다. 합성 호출/간호 기록/진료 상태 fixture의 삭제 허용·제한도 확인한다.
6. DevTools에서 1440px 데스크톱, 393px 너비를 설정한다. 로고 +20px, 메뉴 접근, 입력·슬롯 선택, 표 내부 가로 스크롤(페이지 전체 넘침과 구별), 모달/패널 스크롤과 닫기/확인 버튼, 키보드 포커스를 확인한다. Native 캘린더 외형 차이는 기록된 대응이다.
7. Console/Network에서 favicon 404와 메시지 채널 오류의 URL·발생 동작·업무 영향만 기록한다(개인정보/요청 본문 공유 금지). 확장 프로그램 원인 여부는 사용자가 준비한 확장 없는 별도 프로필과 대조한 후 판단한다. 현재 사용자 프로필의 확장/보안 설정을 임의로 변경하지 않는다.

## 인계
